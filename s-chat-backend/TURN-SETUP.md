# S-Chat TURN + WebSocket production setup

S-Chat uses **two different real-time channels**:

- **WSS WebSocket (`/ws`)**: chat delivery and WebRTC signaling (invite, accept, SDP offer/answer, ICE candidates).
- **TURN**: WebRTC media relay when two browsers cannot establish a direct peer-to-peer path.

They are not the same service. The browser connects to the S-Chat backend over WSS; the browser then connects to coturn for TURN media relay.

## 1. Deploy coturn

Use a small Linux VPS with a stable public IPv4 address. Give it a hostname such as `turn.example.com`.

Recommended ports:

- UDP 3478 — TURN/STUN
- TCP 3478 — TURN/STUN fallback
- TCP 5349 — TURN over TLS (`turns:`)
- UDP relay range, for example 49152-65535 — media relay ports

If your firewall/provider allows it, keep the relay range as narrow as your capacity permits.

## 2. Use REST-style temporary credentials

Generate a strong random shared secret. Configure coturn with the same secret and REST authentication, for example:

```ini
listening-port=3478
fingerprint
lt-cred-mech
use-auth-secret
static-auth-secret=REPLACE_WITH_A_LONG_RANDOM_SECRET
realm=turn.example.com
server-name=turn.example.com
```

For TLS, configure your certificate/key and enable the TLS listener on 5349. Follow coturn's current documentation for certificate paths and your Linux distribution's service configuration.

Do **not** use a permanent username/password in frontend JavaScript.

## 3. Configure Render

Set these backend environment variables in Render:

```text
TURN_URLS=turn:turn.example.com:3478?transport=udp,turn:turn.example.com:3478?transport=tcp,turns:turn.example.com:5349?transport=tcp
TURN_SHARED_SECRET=THE_SAME_RANDOM_SECRET_USED_BY_COTURN
TURN_CREDENTIAL_TTL_SECONDS=3600
```

The shared secret remains backend-only. `/api/auth/ws-ticket` and `/api/calls/ice-servers` are authenticated endpoints.

The frontend receives only short-lived TURN credentials generated by the backend.

## 4. WebSocket signaling setup

The production frontend uses:

```text
wss://s-chat-u8fs.onrender.com/ws?ticket=<30-second-one-time-ticket>
```

The access JWT is **not** placed in the WebSocket URL anymore. The frontend first calls:

```text
POST /api/auth/ws-ticket
X-S-Chat-Client: web
Authorization: Bearer <access-token>
```

The backend returns a 30-second WebSocket ticket. The handshake consumes that ticket once.

This reduces the impact of reverse-proxy/access-log leakage of WebSocket URLs.

## 5. Do you need TURN over WebSocket?

Normally, **no**. WebRTC browsers can use TURN over UDP, TCP, and TLS. For difficult networks, `turns:` over TCP/TLS is usually the important fallback.

TURN-over-WebSocket is a specialized transport and should only be enabled if you have a specific network/proxy requirement. Do not confuse it with S-Chat's WSS signaling WebSocket.

## 6. Test the call path

Test in this order:

1. Two users must be friends.
2. Both users must be logged in.
3. Both browser pages must be HTTPS.
4. Both users allow microphone/camera permissions.
5. Verify `/api/auth/ws-ticket` succeeds.
6. Verify the WSS connection opens.
7. Verify `/api/calls/ice-servers` returns STUN plus TURN credentials.
8. Make a voice call on two different networks (for example, Wi-Fi vs mobile data).
9. Repeat with video.
10. In browser WebRTC diagnostics, confirm an ICE candidate pair becomes selected. A relay candidate (`typ relay`) demonstrates TURN is being used.

## 7. Security rules

- Never put `TURN_SHARED_SECRET` in Vercel/frontend files.
- Never put the Supabase service-role key in frontend files.
- Keep the TURN server patched and firewall unnecessary ports.
- Use TLS for the TURN hostname when using `turns:`.
- Rotate the TURN shared secret if you believe it was exposed.
- Rotate `JWT_SECRET` if the application's signing secret is exposed; this invalidates existing JWTs.
